Approach

Start with the problem, not the tool

A systems engineering way of working, scaled to the size of the problem.

  1. 1

    Understand the problem and the users

    Who makes the decision, how often, and what goes wrong today? A seller needs a call list, an auditor needs evidence, a manager needs a trend.

  2. 2

    Design the system

    Map the data flow, agree on definitions, decide who owns each part, and place the controls where errors start.

  3. 3

    Build what fits

    A report, a daily list, an alert or a small app. Best practice, but only as much as the problem needs.

  4. 4

    Verify and improve

    Quality gates before data is written, tests before release, and feedback from the people who use it.

Solvi: from rooftop to kilowatt-hour

In progress

Solvi is a fictional Nordic solar and battery installer. All data is generated.

One data system for a company where sales, installation, service and quality all depend on the same facts, but each needs a different answer. Installations, production, weather, battery deliveries, crews, safety events, compliance records and contracts are joined once, checked once, and then delivered in the form each group can act on.

Project planningWhat changes after the customer signs?Components dropped or downsized after the site survey
SellersWho is waiting to hear from us?A short list of open proposals nobody has followed up
Customer serviceWhat has this customer bought, ever?One search across the old and the new ERP

Try the working example. Three apps, one for each group of users, built on six data domains with a shared core.

Open demo Code on GitHub
System choices
  • One definition per number, shared by every view
  • Quality gate: nothing is written if a check fails
  • Weather and snow in the model, so faults are not confused with cloudy weeks
  • Compliance stored as data: requirement, due date, evidence, deviation
  • Old ERP history kept in a frozen, searchable archive, mapped to new numbers
  • Battery risk: act on conditions across the chain, not on "days since last incident"
  • Six data domains with clear owners, sharing through shortcuts instead of copies
  • Everything in Git, with separate test and production

Principles

Best practice, sized to the problem

The right-sized answer

Not every problem needs a platform. Sometimes a checklist or one well-placed alert does more than a dashboard.

Controls where errors start

Checking at the source is cheaper than explaining a wrong number later. Validation runs before data is stored.

Clear ownership and definitions

Every number has one definition and an owner. That is what lets people trust it, and what makes data ready for AI.

Built with the people who use it

Test early with real users. The small details, like always knowing the next step, decide whether a system is used.
